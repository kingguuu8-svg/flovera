# 待解决问题

这份文档记录当前路线中还没有完全收敛、但必须持续盯住的问题。

## 1. 防止架构劣化

### 问题

AI 很容易把原型写成“能跑但不可维护”的系统：

- 逻辑重复
- 局部补丁越来越多
- 接口不稳定
- 工具链 workaround 进入核心实现
- 业务层和执行层互相耦合

### 需要解决的事

- 哪些模块必须冻结接口
- 哪些能力必须通过协议表达，而不是自由代码实现
- 哪些改动必须先过测试和回滚点
- 哪些 workaround 只能放在工具链层，不能进入核心实现

### 当前判断

- 核心执行面还算清楚
- 外围工具链和兼容层已经开始膨胀
- 如果没有明确边界，后续很容易演化成补丁堆

## 2. 借鉴成熟实现而不是照抄

### 问题

借鉴成熟沙箱设计时，容易混淆两件事：

- 借鉴设计原则
- 照抄具体实现

Android 普通 App 不能直接照抄 root、系统权限、内核控制路径。

### 需要解决的事

- 选哪些成熟案例作为主参考
- 哪些抽象可以沿用
- 哪些平台相关实现必须为 Android 重写
- 哪些能力只能作为长期预留，不能进入第一阶段

### 候选参考

- Android Virtualization Framework
- Firecracker
- gVisor
- Flatpak
- Crostini / Termina

### 当前收缩

第一阶段不再继续扩大“沙箱平台”设计空间。当前主线收缩为：

```text
Android thin controller
  -> QEMU runtime
  -> fixed Linux guest image
  -> guest 内 agent + /workspace
```

这意味着成熟案例主要用于确认边界和风险，不用于复制实现。`QEMU` 是第一阶段唯一执行底座，`bridge` 只是最小控制通道，workspace 语义优先由 guest 内 agent 和 Linux 工具链承担。

## 3. 前端如何表达、编辑并控制 AI 执行环境

### 问题

当前前端构想不是传统意义上的“聊天框 + 结果页”，而是一个可编辑的工作空间。这个工作空间需要同时满足几件事：

- 前端元素本身可编辑、可组合、可序列化
- 前端元素可以被打包成命令或事件，交给后端执行
- 后端不仅能响应前端，还能反过来完整操作前端
- 前后端之间不应该绑定到某个具体 harness，实现层要尽量可替换
- 元素结构需要支持树状嵌套，而不是平面列表
- 布局需要受约束，不能退化成自由画布或任意 SVG 排版

这意味着前端不是单纯的展示层，而是一个“对象化的执行界面”。如果定义不好，后面会同时出现两个问题：

- UI 很快变成无法维护的自由拖拽画布
- 后端协议很快变成把 shell 命令、布局命令、状态更新揉在一起的混合层

### 需要解决的事

- 前端最小元素集是什么
- 元素如何表示父子关系和嵌套关系
- 元素如何绑定命令、状态和回写结果
- 前端到后端的消息协议怎么定义
- 后端到前端的回写协议怎么定义
- 哪些布局能力允许后端控制，哪些必须由前端固定
- 哪些操作应该是命令，哪些应该是状态更新，哪些应该是布局变更
- 如何保持后端 harness 可替换，而不是把某个实现写死进 UI

### 初步判断

这一层最适合借鉴的是三类成熟模型，而不是直接抄某一个产品：

- Notion 的 block tree，用来表达树状嵌套
- Blockly 的 block 和字段模型，用来表达可编辑、可序列化、可绑定动作的元素
- Figma auto layout，用来表达格子化、模块化、受约束的排版

### 当前方案倾向

第一版不应该做自由画布，也不应该做复杂 SVG 编辑器。更合理的是：

```text
block tree
  -> controlled action
  -> guest agent in QEMU workspace
  -> result / log / patch
  -> frontend update
```

也就是说：

- 前端负责展示 block tree，并允许有限编辑
- guest 内 agent 负责解释工作区命令、执行动作、返回结果
- 布局只允许少数稳定模式，例如 `vertical`、`horizontal`、`grid`
- 元素类型只允许少数基础类型，例如 `container`、`button`、`text`、`log`

### 当前风险

- 如果前端允许太自由的布局，很容易走向不可控的屎山 UI
- 如果 Android 端直接接受任意 shell 字符串，会失去控制边界
- 如果布局、命令、状态更新不分层，后续很难回滚和审计
- 如果一开始就追求“完全灵活”，实现复杂度会远高于当前阶段需要
- 如果在 guest agent 稳定前先做完整前端协议，会重新走向过度设计

### 子问题：自由块 / WebView 怎么处理

除了结构化块之外，前端还可能需要一个“自由块”，用来承载更接近网页或富媒体的内容，例如：

- 图片
- 视频
- 图表
- 复杂交互
- AI 生成的独立小页面

这类内容不适合完全塞进结构化 block tree 里，更适合由 `WebView` 或类似嵌入容器承载。

#### 需要解决的事

- 自由块是否作为一种特殊 block 类型存在
- 自由块是否允许加载本地页面、远端页面或 AI 生成页面
- 自由块如何和后端通信
- 自由块如何限制权限，避免破坏整个工作台的协议边界
- 自由块能否改变宿主布局，还是只能被宿主控制大小和生命周期

#### 当前判断

- 自由块可以存在，但必须是受控的自由块
- 它适合承担展示和复杂交互，不适合承担主工作区骨架
- 最合理的结构是“结构化工作台 + 局部自由内容嵌入”

### 设计倾向：block 树打底，WebView 优先

当前更合理的产品方向不是用 `WebView` 取代 `block tree`，而是让 `block tree` 作为底层骨架，再把 `WebView` 作为优先级最高的内容块之一。

#### 正式表述

- `block tree` 是底层数据结构，负责嵌套、组合、父子关系、权限边界、序列化和回写
- `WebView` 是 `block` 的一种高优先级类型，适合承载主内容、复杂交互和富媒体
- 其他 `block` 负责控制、日志、状态、版本和输入输出
- `WebView` 不能反过来决定整个 workspace 的结构规则，只能在宿主允许的边界内活动

#### 当前判断

- 先把树状结构打牢，后面所有内容都挂在树上
- 第一版可以把 `webview` 放在最重要的位置，但不能丢掉 `block` 结构
- 最合理的第一阶段产品形态是“`block` 化工作台 + `WebView` 主内容块”

## 结论

后续实现必须围绕这些问题做取舍：

1. 是否会让系统变成不可维护的补丁堆
2. 是否只是照抄了不适合 Android 普通 App 的实现路径
3. 前端是否仍然保持 block 化、协议化、受约束，而不是演化成自由画布或混合脚本层
4. 是否偏离 QEMU guest workspace runtime 主线，重新变成自制沙箱平台

只要答案不明确，就先停在文档和 guest 工作机验证层，不扩大 Android、bridge 或前端实现面。
