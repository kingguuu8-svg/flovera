## Hermes Research Summary

User asked to stop over-designing Anthropic-only routing and instead study Hermes provider architecture.

Local Hermes source zip was extracted under:

- E:\main\_research\hermes-agent-main

Important Hermes paths inspected:

- providers/base.py
- providers/README.md
- plugins/model-providers/README.md
- plugins/model-providers/deepseek/__init__.py
- plugins/model-providers/custom/__init__.py
- plugins/model-providers/anthropic/__init__.py
- plugins/model-providers/openrouter/__init__.py
- agent/transports/chat_completions.py
- agent/transports/anthropic.py
- agent/anthropic_adapter.py
- website/docs/developer-guide/adding-providers.md

Key conclusion:

Hermes does not use two user-visible loops. It uses one agent loop, multiple API-mode transports, and declarative provider profiles. The profile declares endpoint/auth/model/request quirks; the transport reads the profile.

Architecture to copy into Flovera:

Flovera Agent Loop
  -> ModelProviderProfile registry
      -> apiMode = chat_completions | anthropic_messages | later others
      -> provider metadata and request quirks
  -> transport/client creation
  -> normalized tool/session behavior stays consistent

Avoid copying Hermes Python wholesale. Reimplement the small subset in Kotlin and keep Koog integration until a specific limitation forces a Flovera-owned transport.

## Current Provider Direction

Short-term path:

1. Keep one Flovera/Koog agent loop.
2. Expand ModelProviderCatalog into a profile registry.
3. Treat custom-openai as a profile-driven OpenAI-compatible slot.
4. Add provider-specific request hooks gradually where Koog allows.
5. Only add Anthropic Messages transport after the profile registry is stable.
6. Do not create a second agent loop unless there is a proven blocker.

Why:

- Two loops would likely create inconsistent session/tool behavior.
- Existing mainstream implementations converge on one loop with adapter/transports.
- Hermes validates this direction.
